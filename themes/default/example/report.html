Design, versioning, caching and access control for a link that keeps working.

Abstract

A link sent in a calendar invite outlives the slide it points at. Most publishing tools answer this by keeping a mutable page behind a stable address, so every edit silently rewrites what a reader will see next week. rshow takes the other side: a publish writes a numbered version, a version never changes, and the address that follows the newest version is a separate promise from the address that holds one. This paper describes the design we ship, the record an artifact carries, the caching rules that follow from immutability, the share model that decides who may read a link, and the experiment we would run to test the claim that a republish sends only what changed.

Design

rshow publishes a folder. The command reads the folder, runs the optional build command if rshow.json names one, hashes every file, writes a manifest, uploads what the host does not already hold and records a version. There is no application server holding the bytes, and no state on the reader's side beyond an ordinary HTTP cache. A published artifact is static files plus a record, which means the reader's browser does the same work it does for any other page, and the host does the work an edge runtime does well. The reading side stays stateless in the sense Fielding argues for, so a version can be served by any node that holds the bytes.

Three addresses come out of one publish: a versioned path that holds the bytes of that publish, a slug path that follows the newest version, and an optional pin that holds a chosen version in place. The three are different promises and the page states which one it is showing.

The artifact record

The record is small and it is the only mutable object in the system: one row per slug, holding the title, the owner, the mode, the newest version number and the pin if there is one. A version is a row of its own under the slug, with its label, its file count and byte count; a manifest is a list of path to hash, size and content type, kept beside the version and enough to rebuild the artifact on another host. A publish inserts the version row only while the newest number is still the one it read, so two writers cannot take the same number: the loser is answered with a conflict and publishes again.

Content addressing does the rest. A file is stored under the hash of its bytes, so the same picture in two decks is stored once, and a republish of an unchanged file is a lookup that finds the hash already present.A hash is the SHA-256 of the file bytes, written in hex. The store keys a file by that value, so identical bytes are stored once whatever their name.

Versioning

A version is a promise that the bytes behind its path will not change. rshow keeps that promise by never writing to a versioned path twice: a publish allocates the next number and writes its files there. Publishing the same content again does raise the number, but it sends no new bytes, because every hash in the manifest is already in the store. Versions are therefore dense, ordered and comparable, and a reader who cites one can be sure the artifact is the artifact. That is the old advice about persistent identifiers taken literally.

Slugs and versions

A slug is the human name of the artifact and a version is a number under it. The slug path is the one that moves, and it is the only address that needs any coordination. A version path is a pure function of the slug and the number, so it can be computed, cached and shared without asking the host anything.

Pins

A pin holds one version at the slug path while later publishes go on behind it. It is one line in the record and it can be moved or removed in a single write, which matters during the last hour before a talk, when the link in the room must not change but the folder still does. Without a pin the slug path follows the newest version and a reader sees the next publish with no warning.

Caching

Immutability is what makes a long cache lifetime safe. The bytes at a versioned path never change, so a browser may keep them for a year and an edge may keep its own copy for five minutes. The live path is the opposite: it is the one address that must be rechecked, so its own lifetime is zero and an edge may answer from a copy for no longer than fifteen seconds.

The cost of a publish follows the same rule. Let the files of a version be files(n) and let the host's store be the set of hashes it already holds. The bytes a publish must send are the size of every file whose hash is missing from the store.

bytes(n) = sum of |f| for f whose hash is new

The equation is the whole reason a republish of a mostly unchanged deck is cheap, and it is also why the first publish is expensive: on the first publish the store is empty, so every file is new. A cache may keep a versioned response for a year and must recheck the live link on every use; an answer to a signed-in reader is never stored by anyone.Revalidation is a conditional request: the browser sends the entity tag it holds and the host answers 304 Not Modified while the bytes still match.

Access control

Reading is decided by two things: who is asking and the mode of the artifact. Every reader signs in through Cloudflare Access, so the host is handed a verified email address before it looks at the artifact. The mode and the share list live in the record, so changing either is one write and never a re-publish.

There are three modes. Private is the default and answers to the owner and to the addresses named with the editor role. People answers to every address named on the artifact, viewer or editor. Public answers to anyone with the link and asks for no sign-in at all.

Shares

A share is one row: an address and a role. An editor may publish a new version and move the pin; a viewer may only read. Only the owner shares, renames or deletes. An address that is not on that list has no way in, whatever it is signed in as.

The check happens in the Worker, before a byte of the artifact is read, which keeps it off the storage path. The request carries the Access session cookie, the Worker verifies it and reads the email claim, and the mode and the shares decide whether the request continues. A signed-in reader who may not read gets a page that names their address, and a reader with no session is sent to the sign-in page and back to the path they asked for.

What there is not

There is no per-link grant and no expiring share URL. The only way to read a non-public artifact is to be a signed-in address the record names, so a closed artifact is closed by the identity provider and the share list, not by a token in the URL. Bearer tokens do exist, but only for the admin API on the other hostname: they publish and manage, and they never open a viewer page.

Evaluation

We have not run a controlled study of rshow, so this section describes the experiment we would run and shows the shape of its result with example data. The claim under test is narrow: after the first publish, the bytes a republish sends track the bytes that changed, and not the size of the folder. A reader should treat every number below as illustrative.

What we would measure

Take one folder of a fixed size, edit it as a person edits a talk, publish after every edit and record the bytes the upload sent, the time to first byte at the slug path, and the size of the record. Repeat with the cache cold and warm, because the two answer different questions: a cold cache measures the host, a warm one measures the reader. Discussion

Immutability buys a link a reader can cite and costs the writer the habit of the newest link. The pin exists because the two are both wanted on the same day: the room reads a fixed version while the folder moves behind it. The trade we have not solved is deletion. A version that never changes is also a version that is hard to withdraw, and a link that has reached one reader can be deleted from the host but not from the copy that reader kept.

The design leans on the fact that static bytes are the cheapest thing a network can serve. That is the same bet the Carbon design system makes about interfaces: one system, few moving parts, and the plainest possible answer to a question a reader asks. The theme in this repository is that bet applied to a page, and its two modes are one system read under two grounds.

Two limits are worth naming. The first is the record: one row per slug is easy to read, and the version insert assumes one writer at a time. Two people publishing the same slug in the same second will resolve to one of the two versions, and the loser is told to publish again. We take that over a lock, because the case is rare and the recovery is cheap.

The second is trust. A version is immutable because the host says so, and nothing in the link proves it. A reader who needs more than the host's word can hash the files they received and compare the result with a manifest they were given, and rshow keeps a manifest for every version; what it does not do is print those hashes on the page, because that costs a reader attention and answers a question most readers do not ask.
