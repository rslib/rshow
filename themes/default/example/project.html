Abstract

A link sent in a calendar invite outlives the slide it points at. Most publishing tools answer this by keeping one mutable page behind a stable address, so an edit made tonight silently rewrites what a reader opens next week. rshow takes the other side. A publish writes a numbered version of the folder, a version never changes once it is written, and the address that follows the newest version is a separate promise from the address that holds one version in place. This paper describes the design we ship, the record an artifact carries, the caching rules that follow from immutability, the share model that decides who may read a link, and the experiment we would run to test the claim that a republish sends only what changed.

Key results

We have not run a controlled study, so the two exhibits below are example data. They show the shape of the claim rather than a measurement of any host: after the first publish, the bytes a republish sends track what the edit touched, not the size of the folder.

Example data: one publish of the folder in the figure above, timed with the host's store empty and then holding the bytes.
Step Cold store Warm store
Hash the folder 310 ms 310 ms
Upload the missing files 4.2 s 41 ms
Write the version record 12 ms 12 ms

The hash and the record cost the same either way, because they are reads and one small write. The upload is the whole difference, and it is also the reason a republish of a folder left alone sends nothing.
